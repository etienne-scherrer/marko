# Devil's Advocate Review: capture-suppressed-error-reasons

## Critical (Must fix before building)

1. **Task 003 contradicts an existing test.** `packages/cache-file/tests/Unit/FileCacheDriverTest.php:401` (`leaves no orphan tmp file when the rename step fails`) asserts `set()` returns `false`. The plan makes `set()` throw. The worker has to rewrite that test, not add a second one next to it, or the suite goes red. The existing test already shows how to force the rename failure: make `{cachePath}/{xxh128(key)}.cache` a directory.

## Important (Should fix before building)

2. **Task 003: changing the exception type breaks BC for callers that catch `RuntimeException`.** `ensureDirectoryExists()` throws `RuntimeException` today, and the `@throws InvalidKeyException|RuntimeException` docblocks on `set()` and `increment()` say so. `CacheException` extends `\Exception`, not `RuntimeException`, so `catch (RuntimeException)` stops matching. Also, `CacheInterface::set()` documents only `InvalidKeyException`, and `setMultiple()` now aborts partway through on a write failure. Fix: update the `@throws` on `set`, `setMultiple` and `increment`, and state the behaviour change in the docs (task 006).
3. **Task 003: concurrent directory creation.** Only calling `mkdir()` when `!is_dir()` leaves a TOCTOU window. A concurrent creator can win, `mkdir()` then fails with "File exists", and the driver would throw. You must re-check `is_dir()` after a failed `mkdir()`, the same way `DiscoveryCache::write()` does. The existing test at line 441 covers the pre-created case but not the race.
4. **Task 003 / 004: don't base failure tests on `chmod`.** Running as root defeats `chmod`-based tests. The existing `IndexCacheTest.php:1091` test (`mkdir 0000`) has no root guard. New tests should block paths with files or directories instead: a regular file where the cache dir should go makes `mkdir` fail with "Not a directory", and a directory at the target makes `rename` / `file_put_contents` fail with "Is a directory". `IndexCache::invalidate()` can't be blocked that way, because a directory at the path makes `is_file()` false and the unlink is skipped. That test needs a `.marko` dir set to 0555 and a skip when `posix_geteuid() === 0`, the same pattern `DiscoveryCacheTest.php:436` uses.
5. **Task 004: `invalidate()` throws a misleading exception and isn't declared.** If `cacheDirUnwritable()` is reused, the message is "Cannot write to index cache" with context "While building or saving". That's wrong for a removal. `IndexCacheInterface::invalidate()` also declares no `@throws`. Fix: add an `IndexCacheException::cacheNotRemovable(string $path, ?string $reason = null)` factory, and add `@throws IndexCacheException` to both the interface and the implementation. A grep found no current callers of `invalidate()`, so nothing else has to change.
6. **Task 004: two unserialize sites.** For a corrupt cache, `isStale()` → `loadTrackedPathsFromDisk()` unserializes before `load()` ever does. Both `@unserialize` calls, the `@file_get_contents`, and the `(string) file_get_contents()` in `load()` (which has no `@` but can still warn) need `ErrorCapture`. Otherwise the "no warning" test passes or fails depending on which path runs first.
7. **Task 002: `$host` is unknown in `enableTls()` for injected streams.** `TestableStreamSocket::injectStream()` (StreamSocketTest.php:14) sets `$stream` without calling `connect()`. Fix: store `protected ?string $host = null` in `connect()`, clear it in `close()`, and fall back to a placeholder such as `'unknown host'` when it's null.
8. **Task 002: a STARTTLS failure test can hang or flake.** If the loopback server never writes, the TLS handshake blocks until `default_socket_timeout`, which is 60s. Spell out the recipe: create `stream_socket_server('tcp://127.0.0.1:0')`, connect, `stream_socket_accept()` the peer, write a plain-text line such as `"220 not tls\r\n"` to it and close it, then call `enableTls()`. The "wrong version number" OpenSSL warning then shows up reliably.
9. **Task 002: where the reason comes from.** `stream_socket_client()` fills `$errstr` for OS-level failures but leaves it empty for DNS or pre-connect failures, where only the warning (`getaddrinfo ... failed`) has the detail. Specify: use `$errstr` when it's non-empty, otherwise the captured warning. Also, port 1 isn't guaranteed to be closed. Bind an ephemeral port, close it, then connect to it.
10. **Task 005: the memoization sentinel collides with the result.** A memoized `?string` reason, where null means reachable, can't use `static $x = null; if ($x === null)`, because when Redis is up it re-probes on every call. Use a separate `static bool $probed`. Also define the message for the null reason (the reachable case): it shouldn't contain a dangling `: `.

## Minor (Nice to address)

- Task 001 already looks partly implemented in this worktree. `packages/core/src/Support/ErrorCapture.php` and `tests/Unit/Support/ErrorCaptureTest.php` exist, and the tests include an extra `resets a reason left over from an earlier call`. `DiscoveryCache::capturing()` is still present. The worker should continue from that state, not recreate it.
- `ErrorCapture` swallows every error level, including `E_DEPRECATED`, raised inside the operation. That's fine for single built-in calls. The docblock should warn callers to wrap only the single failing call, not larger blocks.
- The task 003 requirement `it creates the cache directory on first write` duplicates the existing tests at lines 451 and 461.
- `DiscoveryCache` keeps `@unlink($tmp)`, and FileCacheDriver keeps `@unlink($tempPath)` (PHPUnit reports `@`-suppressed source warnings, but only when the cleanup itself fails). That's consistent, but it's worth listing in the PR follow-ups.
- When the cache is valid, `IndexCache::load()` unserializes the whole payload twice: once in `isStale()` and once in `load()`. This was already the case before this plan and is out of scope.

## Questions for the Team

- Task 003: should `FileCacheDriver::set()` really throw on write failure, when other drivers return `false` and `CacheInterface` only documents `InvalidKeyException`? Throwing follows the "loud errors" principle, but a full disk would now cause a 500 in callers such as page-cache and ratelimiter that used to degrade gracefully.
- Should `FileCacheException` extend `CacheException`, and so lose `RuntimeException` compatibility? Or should the plan accept the BC break and document it?
