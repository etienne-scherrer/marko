# Plan: Destructive db commands allowlist

## Created
2026-10-05

## Status
completed

## Objective
Allow destructive database commands (`db:rebuild`, `db:reset`, `db:rollback`, `db:seed`) freely only in development and testing; in any other non-production environment require `--force` (plus a confirmation when someone can answer); keep production blocked with no override. Implements option C, the recommendation of #235.

## Related Issues
Closes #235

## Discovery Notes
- `AppEnvironment` (core) has `isProduction()` (`production`, `prod`, unset) and `isDevelopment()` (`development`, `dev`, `local`). No testing name exists yet.
- Each destructive command checks only `isProduction()` inline, with slightly different messages. `SeederRunner::runAll()`/`runByName()` re-check `isProduction()` and throw `SeederException::blockedInProduction()`.
- `db:migrate` already uses an allowlist (`isDevelopment()`) for generation and uses core's `ConfirmationPrompterInterface` (#225) plus `--force` for destructive generation, returning 1 when nobody can answer and 0 when the user declines. The new guard mirrors those semantics.
- `#[Command(flags: [...])]` must declare `force` so it never consumes the next token.
- `marko/testing` (`FakeConfirmationPrompter`) is already a dev dependency of `marko/database`.
- CHANGELOG.md is generated by `bin/release.sh` below a marker from PR titles; there is no Unreleased section yet. The upgrade note goes in an `## [Unreleased]` section above the marker (release.sh does not touch it, so it is folded into the release entry by hand at release time).

## Scope

### In Scope
- `AppEnvironment::isTesting()` and `TESTING_NAMES` (`testing`, `test`)
- A shared `DestructiveCommandGuard` in `marko/database` used by all four commands
- `--force` flag on `db:rebuild`, `db:reset`, `db:rollback`, `db:seed`
- `SeederRunner` guard following the same policy via a `force` argument, plus `SeederException::requiresForce()`
- Docs (database.md policy table, core.md `isTesting()`), changelog upgrade note

### Out of Scope
- Changing `db:migrate` behaviour
- A production override of any kind

## Architecture Notes
- `DestructiveCommandGuard` (readonly class, `Marko\Database\Command`) takes `AppEnvironment` and `ConfirmationPrompterInterface`; it is autowired. `check(string $command, string $effect, Input $input, Output $output): ?int` returns null to proceed, or the exit code to stop with (1 refused, 0 declined) — the same contract as `MigrateCommand::confirmDestructiveChanges()`.
- Policy: production -> refuse (1) regardless of `--force`; development/testing -> proceed; anything else -> without `--force` refuse (1); with `--force` and an interactive prompter ask, decline -> 0; non-interactive with `--force` -> proceed.
- Per-command `$effect` strings are fixed in task 002 so 003/005/006 agree.
- Unlike `db:migrate`, `--force` here does not skip the prompt when a terminal is attached; the scripted form is `--force --no-interaction`.
- `SeederRunner` cannot prompt (it is called programmatically); it takes `bool $force = false` on `runAll()`/`runByName()`. `SeedCommand` forwards `--force` after its guard approved.

## Risks & Mitigations
- Staging CI scripts break: documented upgrade note in changelog and docs; PR labelled `breaking`.
- Interactive prompt in tests hanging: unit tests use `FakeConfirmationPrompter`; integration cases never pass `--force` in a non-dev environment without `--no-interaction`.
- Existing integration assertions on old messages (tests/Integration/App/MigrationSafetyTest.php): updated in task 005.
