# Devil's Advocate Review: insert-batch-key-matching

## Critical (Must fix before building)

1. **Task 001: reading `@@auto_increment_increment` between `execute()` and `lastInsertId()` can zero out the first id.** `MySqlConnection::lastInsertId()` is `PDO::lastInsertId()`, which wraps the C API `mysql_insert_id()`. That reflects the *last statement* run on the connection, and a following `SELECT` resets it (it does not keep the `LAST_INSERT_ID()` SQL function value). If the worker does `execute(INSERT)` -> `query(SELECT @@...)` -> `lastInsertId()`, every id becomes `0 + offset * step`. The existing spy (`makeBatchSpyConnection`) returns a fixed `firstId` no matter what ran, so unit tests would still pass. Fix: read the step *before* the INSERT (inside the `$write` closure, so still inside the transaction), and call `lastInsertId()` right after `execute()`. Add a unit test whose spy returns 0 from `lastInsertId()` once `query()` has run after the last `execute()`.

2. **Task 001: "explicit keys" can't be detected with `$readsGeneratedKeys`.** `omitsGeneratedKey()` only checks `isGenerated`. For an `autoIncrement` key it is always `false`, whether or not the key is set. The real signal is whether the pk column is in the INSERT: `withoutDatabaseFilledKey()` drops an unset/null auto-increment key, so `array_key_exists($pkProperty->columnName, $allRows[0])` / `in_array($pkColumn, $columns, true)`. A worker who reuses the existing flag will skip arithmetic for every batch or for none.

## Important (Should fix before building)

3. **Tasks 001/002: explicit-id tests must use non-consecutive ids.** For an INSERT with explicit auto-increment values, `mysql_insert_id()` returns the first explicit value. So with consecutive explicit ids (e.g. 1,2,3), the buggy `firstId + offset` arithmetic gives the right answer by accident and the test never fails. Use something like `[10, 50, 30]` (non-monotonic). In the unit spy, make `lastInsertId()` return an unrelated value.
4. **Task 001: the type of the setting's value depends on the driver.** Depending on PDO emulation and stringify settings, `SELECT @@auto_increment_increment AS step` comes back as `int` or as a numeric `string`. Accept an `int`, or a string of digits, that is >= 1. Throw `BatchInsertException` for these cases: no row, missing column, `0`, a negative value, or a non-numeric value. Alias the column: the raw key `@@auto_increment_increment` is awkward and its name differs between servers.
5. **Task 003: the "existing auto-increment batch test" pattern doesn't exist.** `packages/database-pgsql/tests/Integration/GeneratedPrimaryKeysTest.php` only has a uuid `generated_key_tokens` table. The worker must add an `autoIncrement` entity/repository and a table `id INT GENERATED BY DEFAULT AS IDENTITY (INCREMENT BY 5) PRIMARY KEY`. Use `BY DEFAULT`, not `ALWAYS`, so that explicit-id inserts stay legal. Create and drop the table in `beforeEach`/`afterEach` and update the file header's table list.
6. **Task 004: "precise `innodb_autoinc_lock_mode` condition" isn't spelled out.** Give the worker the facts. A multi-row `INSERT ... VALUES` is a "simple insert": InnoDB reserves all of its values at once. They are consecutive (stepped by `auto_increment_increment`) in lock modes 0 and 1. In mode 2 (the default since MySQL 8.0) they are consecutive unless a concurrent "bulk insert" (`INSERT ... SELECT`, `LOAD DATA`) on the same table interleaves. Also say that the step is now read per batch, and that the `Repository::insertBatch()` implementation docblock and inline comment (Repository.php ~304-311, 381-382) must be updated too.
7. **Task 002: MariaDB matrix.** The step-5 test must skip on MariaDB, which uses RETURNING and already has a step-5 test. The explicit-ids test runs on all servers. `SET SESSION` isolation relies on the per-test fresh connection that `afterEach` disconnects. Keep it that way: never set the variable globally.

## Minor (Nice to address)

- `insertBatch()` uses `$entities[0]` and `foreach ($entities as $offset => ...)`, which assumes a list. A non-list array (e.g. keys 3,7) gets wrong offsets or an undefined-key warning. `array_values()` once at the top would harden it.
- One extra round trip per MySQL batch. It could be cached per connection, but the session variable can change, so reading it per batch is the safe choice (as planned).
- Test fakes elsewhere that return `driverName() === 'mysql'` and `supportsReturning() === false` would now need `query()` to return the step. None of the current ones call `insertBatch()`, but watch the full suite.
