**Status**: completed

## Description
Prove the sequence change against a real PostgreSQL server, including a migration file written by `MigrationGenerator` and run by `Migrator`.

## Context
- New file: `packages/database-pgsql/tests/Integration/SerialSequenceWideningTest.php` with its own table (for example `serial_widening_items`). Do NOT reuse `cast_default_items`: tests run `--parallel`, and a table shared with another file races
- Pattern to follow (skip/connection/diff/run helpers, `pest()->group('integration-services')`): `packages/database-pgsql/tests/Integration/ColumnCastsAndExpressionDefaultsTest.php`
- Migrator wiring: no pgsql integration test builds a `Migrator` yet. Follow `packages/database/tests/Migration/Helpers.php` (around line 282, `MigrationGenerator`) and `packages/database/tests/Migration/MigratorTest.php` (`Migrator`, repository, paths). Use a scratch directory for the generated file
- Related source: `packages/database/src/Migration/MigrationGenerator.php`, `packages/database/src/Migration/Migrator.php`, `packages/database-pgsql/src/Introspection/PgSqlIntrospector.php`
- Env: `MARKO_TEST_PGSQL_HOST` etc. via `tests/Fixtures/IntegrationDatabase`
- Assert the sequence directly: `SELECT data_type, max_value FROM pg_sequences WHERE ...` (expect `bigint` / `9223372036854775807` after widening, `integer` / `2147483647` after narrowing), in addition to the inserted ids
- Atomicity setup: keep every row id within integer range and push only the sequence past it (`setval(..., 2147483648)` after inserting and deleting a row, or `setval` without a matching row). Then the down migration's `ALTER COLUMN ... TYPE INTEGER` succeeds and only `ALTER SEQUENCE ... AS integer` fails. Assert the column is still `bigint` AND the sequence is still `bigint` afterwards. A row id over the limit would fail at the column step and prove nothing about the single statement
- Unowned-sequence setup: detach the serial's own sequence with `ALTER SEQUENCE <table>_id_seq OWNED BY NONE`, keeping its `_seq` name. `PgSqlIntrospector::isSerial()` flags auto-increment only when the default contains `nextval(` and `_seq`; a differently named sequence makes the diff throw `columnChangeNotSupported` before the `DO` block runs. Assert the thrown exception message contains the table and column names
- Identity setup: `generateCreateTable()` always emits `SERIAL`, so create the identity table with raw SQL (`id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`)
- Cleanup (`beforeEach` and `afterEach`): `DROP TABLE IF EXISTS` for the test table, `DROP SEQUENCE IF EXISTS` for the detached sequence (it survives `DROP TABLE` once `OWNED BY NONE`), and drop the migrations repository table and scratch files that the Migrator test creates

## Requirements (Test Descriptions)
- [x] `it widens the sequence with an integer key so ids pass 2147483647`

- [x] `it widens an identity key and its sequence`

## Acceptance Criteria

- Tests skip without `MARKO_TEST_PGSQL_HOST`

## Implementation Notes
Kept the tests in `ColumnCastsAndExpressionDefaultsTest.php`, the file the issue names, in their own describe block. No other test file uses `cast_default_items`, and Pest parallelises per file, so the table is not shared. The unowned-sequence case uses a separate `cast_default_items_loose_seq` (its name keeps `_seq`, so the introspector still sees an auto-increment column). Leftovers (mixed-case table, migrations table, loose sequence) are dropped before and after each test. Verified red against the old generator (5 of the new cases fail) and green on PostgreSQL 17.
