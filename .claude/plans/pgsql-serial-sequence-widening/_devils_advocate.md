# Devil's Advocate Review: pgsql-serial-sequence-widening

Note: at review time `PgSqlGenerator.php` in this worktree already contains `generateSequenceFollowingTypeChange()` and `PgSqlGeneratorTest.php` already calls a `pgsqlSequenceTypeChange()` helper, so task 001 appears to be in progress. Findings below are written against the plan and checked against that code.

## Critical (Must fix before building)

None. The plan is small and the dependency order (001 -> 002, 001 -> 003) is correct.

## Important (Should fix before building)

1. **Task 001 - `pg_get_serial_sequence()` argument parsing is unspecified.** The first argument is parsed as a (possibly schema-qualified) identifier and lower-cased unless double-quoted; the second argument is taken literally. The generator always emits `"$table"`, so the table literal must be `'"posts"'` (double quotes inside the string literal) or a mixed-case table gets a NULL sequence and the migration raises the "no owned sequence" error for a serial column that does own one. The column argument must NOT be double-quoted. Added a requirement test for a mixed-case table name.
2. **Task 001 - the sequence name must be spliced with `format('%s')`, not `%I`.** `pg_get_serial_sequence()` returns an already quoted, schema-qualified name (`public.posts_id_seq`); `%I` would quote it as a single identifier and fail. Added to requirements.
3. **Task 001 - existing unit tests change.** Two existing tests expect a plain `ALTER TABLE` for an auto-increment key whose type changes ("does not drop NOT NULL on an auto-increment primary key declared nullable in PHP", and the nextval-default widening test near line 800). The task did not list them; a worker could see them fail and "fix" the generator instead. Also, every alteration produced for that column (for example a nullability change on a non-primary auto-increment column) must sit inside the `DO` block's `ALTER TABLE`, not in a second statement.
4. **Task 001 / plan - escaping and error text.** Escaping was required only for the `pg_get_serial_sequence()` arguments; the `RAISE` message literal embeds the same names and needs the same `''` escaping. The plan's architecture note puts the fix in `HINT`. The exception translator wraps the `PDOException`, and whether the HINT line reaches the message is not verified, so the fix belongs in `MESSAGE`. Updated the note and requirements.
5. **Task 002 - the atomicity test can pass for the wrong reason.** If a row id is greater than 2147483647, the down migration fails at `ALTER COLUMN ... TYPE INTEGER` before the sequence is touched, which proves nothing about the single statement. The test must leave the rows within integer range and push only the sequence past it (`setval` to more than 2147483647, then delete that row), so `ALTER COLUMN` succeeds and `ALTER SEQUENCE ... AS integer` fails. Then assert the column is still `bigint` and the sequence is still `bigint`.
6. **Task 002 - test isolation under `--parallel`.** The plan pointed at `ColumnCastsAndExpressionDefaultsTest.php`, whose table `cast_default_items` is shared with that file's other tests. Parallel workers on the same table race each other. Use a new file and table. A sequence detached with `OWNED BY NONE` survives `DROP TABLE`, so `afterEach` must `DROP SEQUENCE IF EXISTS` it, or the next `SERIAL` create silently gets a `..._seq1` sequence. The Migrator test also needs its migrations table and scratch directory cleaned up.
7. **Task 002 - setup gotchas for the unowned-sequence and identity tests.** `PgSqlIntrospector::isSerial()` (line ~382) flags auto-increment only when the default contains `nextval(` and `_seq`. If the test detaches into a sequence whose name lacks `_seq`, the diff sees a non-auto-increment column and throws `columnChangeNotSupported` instead of reaching the `DO` block. Keep the `_seq` name (use `OWNED BY NONE` on the serial's own sequence), or build the diff by hand. `generateCreateTable()` always emits `SERIAL`, so the identity table must be created with raw `GENERATED BY DEFAULT AS IDENTITY` SQL.
8. **Task 002 - assertions and Migrator wiring.** Success criterion 1 ("AS bigint with max 9223372036854775807") needs a direct `pg_sequences` (`data_type`, `max_value`) check, not just an insert. The generated-file test must build `MigrationGenerator` and `Migrator` the way `packages/database/tests/Migration/Helpers.php` and `MigratorTest.php` do (repository table plus scratch paths). No pgsql integration test does this yet. Added these to Context.

## Minor (Nice to address)

- Identifiers containing `"` or `$$` would break the generated SQL. The generator never escapes `"` anywhere, so this matches existing behaviour. A tagged dollar quote (`$marko$`) would remove the `$$` case cheaply.
- An auto-increment column whose type changes to a non-integer type still gets a plain `ALTER TABLE` (the `SEQUENCE_TYPES` guard). That is acceptable but untested.
- `packages/docs-markdown/docs/packages/database.md` (around line 1604) says a PostgreSQL column change "goes into one `ALTER TABLE`". This is still true for the example shown but no longer true for auto-increment keys. It is out of the requested docs scope.
- The behaviour was probed on PostgreSQL 17 only. Identity-sequence following has been PostgreSQL behaviour since 10, but CI's server version should be confirmed.
